## Open issues

### Top tier — self-fetch from a moving ref

- `tests/e2e/scripts/setup_rootless.sh:4-10` — `curl -LJO "https://raw.githubusercontent.com/k3s-io/k3s/main/k3s-rootless.service"` pulls the systemd unit from `main` of the same repo this script lives in. ### Inline downloads without digest verification

### Advisory — install.sh trust model

`install.sh` and `package/rpm/install.sh` are the user-facing `curl … | sh` recipes. Their `download()` helper (line `install.sh:429`) issues unverified `curl`/`wget`, but the surrounding flow downloads `sha256sum-${ARCH}.txt` from the same `INSTALL_K3S_ARTIFACT_URL` (line `install.sh:468`) and verifies the binary against it (`verify_binary()`, line `install.sh:567`). The risk is rooted in TOFU: anyone who controls the artifact URL controls both the binary and its declared hash. The repo cannot eliminate this without GPG-signing or cosign-signing release artifacts and shipping the verifier in a separately-trusted channel — out of scope for this scan, but worth tracking.

## Retro: dependency types not explicitly covered

### R1. GPG-fingerprint pinning is a missed verifier pattern

**What was seen.** `.github/actions/vagrant-setup/action.yaml:9-16` downloads the HashiCorp APT signing key, then verifies it via `gpg --show-keys --with-colons /tmp/hashicorp.asc | awk -F: '$1=="fpr"{print $10; exit}'` and compares the result against a hard-coded fingerprint constant. The inventory script flagged the curl as "verifier ✗".

**Why current rules missed it.** The verifier-pattern regex in `inventory.py` looks for `sha256sum -c`, `shasum -a 256 -c`, `sha512sum -c`, `cosign verify`, `gpg --verify`, `openssl dgst`, `*_SUM_*` references, and `ADD --checksum=`. A `gpg --show-keys`-then-fingerprint-compare pattern authenticates the downloaded key just as well as `gpg --verify`, but matches none of those tokens.

**Proposed change.** Extend the verifier patterns in `inventory.py`: any command containing both `gpg --show-keys` (or `gpg2 --show-keys`) and a 40-hex string literal in the same ±10-line window counts as a verifier.

### R2. The ±30-line verifier window matches across unrelated downloads

**What was seen.** `Dockerfile.test:77-80` runs `curl -O -L "https://golang.org/dl/${GO_VERSION}.linux-amd64.tar.gz"` followed immediately by `tar -C /usr/local -xzf` with no `sha256sum -c` step. The script reported "verifier ✓" because the kubectl block at `:73-74` and the bento-box block at `:62-66` are inside the ±30-line window of line 77.

**Why current rules missed it.** The verifier scan walks ±30 lines from the download line and reports "verifier present" whenever any verifier match appears in the window. It does not associate a verifier with a *specific* download command — so a verifier for kubectl 4 lines up satisfies the Go-tarball download below it.

**Proposed change.** Tighten the association: a verifier counts only when the filename it references (the argument to `sha256sum -c` after `echo "<digest>  <file>"`, or the path in `--checksum=`) matches the output filename of the candidate download (the `-o`/`-O` argument, the `>` redirect target, or the inferred basename of the URL). When the verifier mentions a different filename, treat the download as unverified even when other downloads in the window are properly verified. Equivalent rule for `${*_SUM_*}` shell variables: require the variable name to share a stem with the download's destination (e.g. `KUBECTL_SHA256` matches a download writing to `./kubectl`, but not one writing to `${GO_VERSION}.linux-amd64.tar.gz`).

### R3. `install.sh` shell-case labels and function-existence checks generate false-positive `wget`/`curl` matches

**What was seen.** The inventory listed twelve "candidate downloads" in `install.sh` and eight in `package/rpm/install.sh` (lines `install.sh:377, 378, 395, 401, 440, 443, 444, 465, 554, 757` and the comments at `install.sh:77-78` and `package/rpm/install.sh:72-73`). Most are case labels (`wget)`), `verify_downloader curl || verify_downloader wget` existence checks, or comments showing the user-facing `curl … | sh` invocation. The single real download flow is `download() → download_hash() → verify_binary()`, which the digest does not surface as such.

**Why current rules missed it.** The candidate-line filter checks for download-shape signals on the command itself (pipes into shell/tar, `-o`/`--output`/`-O` flags, `>` redirect, archive extensions in URL). A bare `wget)` case label has no URL and no flags, so it slips through; a `verify_downloader wget` invocation likewise carries no URL.

**Proposed change.** Two cheap filters:
1. Skip lines where the matched tool token (`curl`/`wget`) appears as a shell case-label (`<tool>)` at end of token) or inside a backticks/`$(...)` substitution that is itself an argument to `command -v`/`which`/a function named like `verify_*`/`have_*`/`exists_*`.
2. Require the line to contain at least one URL-shaped token (`https?://...`, `git://`, `s3://`, `gs://`) OR a non-flag positional argument whose extension matches a download-format set (`.tar`, `.tar.gz`, `.tgz`, `.zip`, `.deb`, `.rpm`, `.box`, `.img`, `.iso`, `.bin`, `.exe`, `.sh`, `.json`, `.yaml`, `.yml`, `.txt`, `.asc`, `.sig`, `.pem`).

### R4. Git-clone scanner does not resolve `${VERSION_*}` shell variables back to a concrete tag

**What was seen.** The script reported `scripts/build:168` and `scripts/build:171` as `branch/tag $VERSION_CNIPLUGINS` and `$VERSION_FLANNEL_PLUGIN` — accurate, but loses the information that `scripts/version.sh` defines them as the literal tags `v1.9.1-k3s1` and `v1.9.0-flannel1`. Same story for the runc/hcsshim/containerd clones in `scripts/download`, where the values come from `go list -m`. A reader of the report cannot tell whether the variable expands to a SHA, a tag, or an empty string without opening the resolver script.

**Why current rules missed it.** The git-clone scanner extracts the raw `--branch` argument and reports the variable name verbatim. It does not source sibling shell scripts (`scripts/version.sh`, `scripts/git_version.sh`) to resolve the variable.

**Proposed change.** When the `--branch` argument is a `${VAR}` reference, resolve it best-effort by grepping sibling files (any `*.sh` in the same directory and one level up) for `^VAR=` assignments. Surface the resolved literal in the digest as a hint: `branch/tag $VERSION_CNIPLUGINS → "v1.9.1-k3s1"`. When multiple assignments appear (different arch branches in `case` blocks), list each. This does not change pinned/unpinned classification — a SHA-shaped value still pins and a tag-shaped one still opens an issue — but the reader can confirm the resolution without leaving the digest.

### R5. yum/zypper repo additions in shell scripts bypass the existing repo-file detector

**What was seen.** `install.sh:586-680` (the `setup_selinux` function and surrounding helpers) constructs a `[k3s-common]` yum/zypper repo entry referencing `rpm.rancher.io` (or `rpm-testing.rancher.io`) and writes it via `cat > /etc/yum.repos.d/...`. The script also runs `zypper addrepo` and `dnf install` against that source. The existing `package_manager_signature_bypass[]` detector scans committed `.repo` / `.list` / `.sources` / `*.kiwi` files, but a repo added at runtime via shell escapes the static detector.

**Why current rules missed it.** The detector targets static files in the repo. A shell-emitted repo entry is generated at install time and never appears as a checked-in `.repo` file.

**Proposed change.** Extend the inventory's shell-script scan to flag patterns that add a package-manager source at runtime: heredocs or `cat >` redirections that write into `/etc/yum.repos.d/`, `/etc/zypp/repos.d/`, `/etc/apt/sources.list.d/`, `/etc/apt/sources.list`, plus invocations of `zypper addrepo`, `dnf config-manager --add-repo`, `yum-config-manager --add-repo`, `add-apt-repository`, `apk add --repository`. For each, classify by whether `gpgcheck=` / `[signed-by=...]` / `--allow-unauthenticated` flags appear in the same block, mirroring the existing static-file rules.

### R6. `tests/e2e/scripts/init.sh:63` is a code-comment false positive

**What was seen.** The digest lists `tests/e2e/scripts/init.sh:63` as a curl candidate; the line is the comment `# Use curl -X GET <IP_ADDR>:5000/v2/_catalog to see cached images`.

**Why current rules missed it.** The candidate-line filter does not strip comments before pattern matching. A `#`-prefixed line is included because the line still contains the string `curl`.

**Proposed change.** Before pattern matching on shell scripts (`*.sh`, `*.bash`, files with `#!/...sh` shebang), strip lines whose first non-whitespace character is `#`. Keep the line offset accurate by replacing the comment text with a blank line rather than dropping it, so reported `file:line` positions remain correct.
